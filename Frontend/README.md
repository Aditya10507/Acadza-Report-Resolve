# Frontend

The faculty review console for the Acadza report-to-fix loop (Phase 3).

## Planned stack

Zero-dependency static site: plain HTML, CSS and JavaScript, with **native MathML**
rendering for the maths. No framework, no bundler, no `node_modules`, no build step.

That is a deliberate choice for the browser client:

- it has no frontend package install or build step;
- MathML is rendered by the browser itself, which is exactly how students see the question.

The static assets are served by the FastAPI application so data and review actions use the
same-origin API.

## Planned files

```
Frontend/
  index.html      # queue + case view
  styles.css      # layout, typography, diff highlighting
  app.js          # focused defect queue, review decisions, API-backed edits
```

The console reads precomputed results (from `Backend/work/console.json`, served
through the authenticated API), so it stays up even if LLM credits run out
(explicitly allowed by the brief).

## Demo login and student panel

```
Frontend/
  login.html       # demo signup / login (student or faculty role)
  login.js
  student.html     # practice panel: the same 43 questions, by subject
  student.js       # practice, answer check, report-question flow, my queries
  student.css      # login + student panel styles (reuses the console palette)
```

- `login.html` is the entry point; accounts are stored in `data/demo.sqlite3`
  (see `../Backend/README.md`). Demo accounts: `student / student123`, `faculty / faculty123`.
- The student panel lists **only the existing 43 questions** from the built dataset —
  no invented content. Each question can be practised (pick an option, check the key)
  and reported with a short statement; queries go through the AI pipeline before
  faculty ever see them.
- The faculty console (`index.html`) is unchanged apart from the session gate
  (redirects non-faculty to the login page), a **Log out** button and a
  **Process queries** button that re-runs the offline pipeline through the API.

## Status

**Built.** The console is complete and verified by jsdom runtime tests (see `../tests/README.md`).

```
Frontend/
  index.html       # focused defect queue, review details and confirmation dialog
  styles.css       # responsive faculty review layout
  app.js           # reports, AI suggestion/score, approve/edit/reject flow

Backend/work/console.json  # fused engine output (regenerate: python Backend/scripts/build_console_data.py)
```

Run it with the FastAPI backend (the console uses the API for data and review actions):

```bash
pip install -r requirements.txt
python run.py --serve-only                 # -> http://localhost:8080
```

The API serves the precomputed console dataset and persists approve/reject actions through
the existing JSON-backed faculty review workflow. It does not run LLM stages; those remain
available through the existing CLI commands. The launcher binds to localhost; do not expose
the API on a public network without adding authentication.

The faculty queue shows only unresolved content defects. Each case contains the student
reports, concise AI suggestion and confidence score, proposed change, and approve/reject
actions. The question and solution context and optional audit note are available when
needed. Manual corrections retain exact-match and answer-format validation before approval.
If an AI edit no longer matches the current content, faculty must enter a fresh correction
instead of approving a stale change.

Non-defect reports are excluded from the faculty queue. Student reply text may be
generated by the existing pipeline, but no student messaging provider is connected;
the console does not claim that replies have been delivered.
